Nexo Assist

An IT service-desk agent, built as the technical challenge of a hiring process.

N-01The challenge

What was asked

A fictional company of about 2,000 employees has an IT team buried in triage: tickets without context, duplicates, wrong priorities, and simple questions waiting in the queue.

The hiring process asked for Nexo Assist, a chat agent that answers questions from the help center, looks up and opens tickets, and hands the conversation to an analyst when needed. On the other side, a console where the analyst takes over with the agent paused, then hands it back or closes it.

The part the brief itself calls the most important: being able to understand, in every answer, what the agent did and why.

Requirements

  • Strict TypeScript; Mastra as the agent framework; any LLM, with the choice explained.
  • Service-desk rules: priority from impact and urgency, deadlines in business hours, no duplicates, reopening within 7 days.
  • A simulated ticket service, separate from the agent, behaving like a legacy system that sometimes goes down.
  • Conversations, tickets and the state of each conversation surviving a restart.
  • Security and privacy (one person's tickets never shown to another) and the cost per conversation under control.
  • Runs locally with a few commands and follows the screen prototype.

N-02Architecture

The system plan

The same structure as the repository's src/. Pick a step and the camera flies to it; on a phone, the steps advance as you scroll.

Swipe the plan sideways to see all of it →

  1. The browser on the left. The layered app in the middle. Around it, the model, the database and the optional pieces. At the bottom, delivery. A dashed line is an optional piece or a configured flow that has not run yet.

  2. Lean DDD. Dependencies only point inwards: app/, agent/ and infrastructure/ depend on application/, which depends on domain/. The domain knows nothing about Next, Mastra or the database, so priority, deadlines and reopening are tested without mocks. Infrastructure implements the application's ports, and a single file wires the pieces together (container.ts).

  3. A Mastra agent with 10 tools: recordUnderstanding, searchHelpCenter, listMyTickets, getTicket, draftNewTicket, draftTicketUpdate, confirmDraft, cancelDraft, offerQuickReplies and transferToAnalyst. The first step is forced to record its understanding (intent, confidence and reason), and code decides which tools exist at each step. The model is Gemini 3.5 Flash; if it fails, the step falls back to Flash Lite and the trace says which model answered.

  4. Drizzle on libSQL: SQLite in development, Turso when deployed. Conversations, messages with their trace, drafts and tickets survive a restart. The legacy ticket system is simulated by a decorator that fails 15% of calls; the service retries without creating duplicates. The search embeddings are cached in the database.

  5. The chat receives each turn as NDJSON: steps, cards and text. The analyst console, and the chat while an analyst is attending, open an SSE stream. The server checks a cheap database signature every second and says when something changed. If the stream drops, the screen falls back to polling on its own.

  6. Production runs on Vercel with the database on Turso, published from a git archive of the latest commit. Alongside it, a Docker image with a smoke test and the CircleCI → Docker Hub → Komodo path. That path is configured but has not run yet: CircleCI starts once the project is connected.

  7. OpenTelemetry tracing with the GenAI conventions, ready for Langfuse, and OpenID Connect SSO (PKCE, state, nonce, JWKS). Both ship turned off and were tested against local servers that follow the protocols, not against real Langfuse, Entra ID or Okta.

  • Dependency, always inwards
  • Orange: agent and models
  • Optional or not run yet
  • Data in motion

N-03What was built

Both sides of the desk

For the employeeSolved without a queue

  • They write the way they talk. The agent searches the help center and asks “Did this solve it?”; the answer feeds the resolution indicator.
  • It finds a ticket without its number and warns when the deadline is at risk (75% of the business-hours deadline), showing the math.
  • It builds a draft with priority and deadline computed in code. Nothing is created before the person confirms; “Change details” recalculates on the server.
  • When three or more people report the same problem within 4 business hours, it raises the impact to “team” without revealing who reported it.
  • High frustration brings up a “Talk to an analyst” button. An explicit request, a critical case, an overdue ticket or doubt that persists hands the conversation over.
  • The “why?” panel on every answer: intent, confidence, reason, tools with input and output, rules that fired, model, tokens and time.

For the analystArriving with context

  • A queue with signals: high frustration, possible mass incident, reason for the handoff.
  • The conversation report: what the person needs, what the agent already did and what is pending. It is built from the history and the traces, without calling the model.
  • Takes over with the agent paused, hands it back or closes it. The database only accepts the change if the state is still the expected one, so analyst and agent never step on each other.
  • “Suggest a reply”: the model writes, the analyst reviews before sending.
  • Everything in real time over the SSE stream, with polling as the fallback.
  • Honest indicators: confirmed resolution kept apart from presumed, not counting open tickets or people who came back with the same problem, and help-center gaps with personal data masked.

N-05Decisions

What I chose, and why

D-01 · model

Gemini 3.5 Flash, checked by a benchmark

I picked Gemini for reliable tool calling (including the tool forced on the first step, which the “why?” panel depends on), low latency with reasoning set to minimal, and a cost of about one US cent per answer.

Then I replaced the qualitative choice with data: I ran the production agent with 7 models, measuring effectiveness, quality (G-Eval with 2 judges), latency and real cost, under a US$ 1.80 cap. GPT-6 Luna tied with Gemini within the confidence intervals and cost 26 times less. I kept Gemini because the gain was in cost, not quality, and switching close to the deadline meant another key. Switching is one environment variable.

7 models · 24 conversations per model · Luna 26× cheaper, same quality · Flash Lite as fallback

D-02 · search

Hybrid search that knows when to abstain

The help center is searched by meaning (embeddings) and by keywords. When the top result does not stand out from the second, the search returns nothing: a look-alike article leads the agent to a wrong answer, and asking is better.

I measured it on 50 questions written the way an employee would, including questions with no right article. A set of 17 was written only after the choice, to check it was not overfitted. On that set the overall score tied, and the report says so.

overall 84% → 94% · held-out set: hit@1 92% → 100% · without the key, falls back to keywords

D-03 · guarantees

Rules in code, not in the prompt

The model decides what to do. Whatever must be guaranteed lives in tested code: priority from the impact × urgency matrix, deadlines in business hours, mandatory and atomic confirmation, reopening only within 7 days, and identity taken from the signed cookie, never from a model argument.

Which tools exist at each step is also decided in code, following the action-selector pattern. A malicious text can change what the model wants to do, but not what it is able to do. The prompt only handles how to talk.

D-04 · measurement

Honest evals

The evals check the database state, not only the text of the answer. Each attack runs 3 times, and passing 1 out of 3 counts as a failure. When Gemini returned a 503 inside the stream, an attack could “pass” without the model having answered; that now counts as a provider failure, reported separately.

The simulated employee (pass^k, as in τ-bench) is published with the result it gave, even when it is low, together with the agent failures it found.

database checked · attacks × 3 · provider failures kept apart · pass^k published as it came out

N-07Delivery

From commit to live

Vercel, in production

The app is live on Vercel, with the database on Turso, behind a temporary access link that goes with the repository to the reviewers. Without the link, no page or API answers.

Each release comes from a git archive of the latest commit, so nothing outside git is uploaded. Usage caps per person, per day and in total are reserved in the database before the model is called.

git · main→deploy-prod.ps1→Vercel + Turso

live

Docker, CircleCI and Komodo

The Docker image (Node 24, non-root, database on a volume) is 486 MB and passed all 25 smoke-test checks: it migrates, seeds the sample data, logs in for real, checks permissions and restarts without losing data.

CircleCI runs types, lint, tests, E2E and the same smoke test, then publishes the image to Docker Hub. Komodo checks the digest of latest every 10 minutes and redeploys. CI never publishes to Vercel.

git · main→CircleCI→Docker Hub→Komodo

configured · not run yet

The smoke test ran locally on 28 Oct 2026. CircleCI has not run any job yet: it starts once the project is connected. docs/DEPLOY.md

N-08Still open

What is left

  • Three agent fixes

    The simulated employee found three behaviours to fix: opening the ticket from a quick reply that was not a “yes”, attaching a new problem to the wrong ticket, and offering an analyst after the ticket already covered the request.

  • CI and CD not run

    CircleCI and Komodo are configured and documented, but they need the owner to connect the accounts. Until then, the evidence for the image is the local run.

  • Model switch

    The benchmark recommends GPT-6 Luna after a confirmation round against Flash Lite. The switch has not been made.

  • Repeated calls

    Tracing showed the model calling the understanding tool several times in parallel on the first step. Only the first one counts, but the others spend tokens.

  • Evals outside CI

    They run by hand because they call the real model. The next step is running them in CI with a minimum threshold.

  • Real services

    SSO was only tested against a fake provider, and tracing against a local collector. Logging out does not revoke the JWT on the server, and the console needs a wide screen.
